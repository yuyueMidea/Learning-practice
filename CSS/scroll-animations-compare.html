00 · 原理总览

谁在算“动画进度”？

所有滚动动画的本质，都是把“滚动位置”映射成“动画进度 p ∈ [0, 1]”，再把 p 映射成样式。两条路线的区别，只在于由谁来做这个映射：是你写的 JS，还是浏览器内置的“滚动时间线”。

JS 路线：监听 → 计算 → 写样式

每次滚动，主线程执行你的回调：读几何信息、算进度、把结果写进 style，再由浏览器走一遍渲染流水线。

scroll 事件 / IO→ 主线程回调→ 读布局
getBoundingClientRect→ 算进度 f(p)→ 写 style→ 样式/布局/绘制→ 合成
■ 主线程　■ 合成器线程
  • 灵活：进度能参与任意逻辑（判断、状态机、联动 Canvas / WebGL）。
  • 现代浏览器的滚动本身在合成器线程完成，JS 回调总是“事后”才执行，因此 scroll-linked 动画天然会滞后一帧，快速滚动时 sticky + 视差容易“漂移”。
  • 主线程繁忙（长任务、布局抖动）时动画会直接掉帧。
  • 优化手段：requestAnimationFrame 合并、passive 监听、读写分离、只改 transform/opacity，以及用 IntersectionObserver 代替 scroll 监听做“触发”。

CSS 路线：把时间换成滚动

普通动画的“时间轴”是时钟；滚动时间线把它换成滚动位置。关键帧不变，只是 currentTime 由滚动进度决定。

滚动位置→ 时间线进度 0–100%→ animation-range 映射→ 关键帧插值→ 合成
■ 主线程　■ 合成器线程
  • 声明式：进度计算、节流、读写时序都交给浏览器。
  • 对 transform、opacity 等可合成属性，动画可以完全在合成器线程运行，与滚动同帧同步，不受主线程阻塞。
  • 注意：动画非合成属性（如 letter-spacing、注册的自定义属性 --n）仍会回到主线程。
  • 限制：只能表达“进度 → 样式”的连续映射，不擅长条件逻辑与一次性触发；需要较新的浏览器。
核心概念含义
animation-timeline: scroll()滚动进度时间线。进度 = 滚动容器已滚动距离 / 可滚动总距离。scroll(root block) 表示根容器的垂直滚动。常用于阅读进度条。
animation-timeline: view()视图进度时间线。进度 = 目标元素穿过滚动容器可视区域的程度。默认以最近的祖先滚动容器为 scroller，view(inline) 取横向轴。
view-timeline / scroll-timeline给时间线命名（如 --lk），其他元素用 animation-timeline: --lk 引用，从而用“A 的位置”驱动“B 的动画”。
timeline-scope命名时间线默认只对声明者及其后代可见；要让兄弟 / 其他分支的元素引用，需要在共同祖先上声明 timeline-scope: --name。
animation-range把时间线的某一段映射为动画的 0–100%。可用 cover / contain / entry / exit / entry-crossing / exit-crossing 加百分比，也可用长度，如 cover 100vh。
animation 简写的坑animation 简写会把 animation-timeline 重置为 auto，所以 animation-timeline 必须写在简写之后。

原理与实现：触发式

它到底是什么

“触发式”是离散事件：元素越过阈值 → 开始播一段有固定时长的动画 → 播完就与滚动无关。JS 路线天生适合，因为 IntersectionObserver 由浏览器在内部异步、批量地计算交叉比例，回调很少，只需要加一个 class，具体动画交给 CSS transition（可合成）。

滚动时间线是连续映射，没有“触发一次”的概念。所以 CSS 版的入场动画其实是“绑定在 entry 范围上的拖动动画”：在元素从视口底部露出的那一小段滚动距离里完成，往回滚就倒放。它很适合“跟手”的入场，但不等于“触发一次”。真正的一次性 CSS 触发属于仍在讨论中的新提案，目前不能依赖。

坑：① IO 的 rootMargin / threshold 决定“何时算进入”；② 没有 JS 时 .rv 被隐藏会导致内容不可见，生产环境应只在 JS 就绪后才加隐藏样式（本页用 data-mode 属性限定）；③ CSS 自定义属性动画（--n）跑在主线程，不是合成动画。

02 · Scroll-linked

动画进度 = 滚动进度

球体缩放/旋转/变色、路径描边、字距伸缩，全部由同一个进度驱动。往回滚会倒放。

原理与实现：滚动联动

模型：sticky 舞台 + 一段“滚动跑道”

外层 .linked 高 400vh，里面的 .stage 是 position: sticky; height: 100vh。用户在这 400vh 里滚动时，舞台被“钉”在屏幕上，而滚动距离就成了动画的“进度条”。关键是算出钉住阶段对应的滚动区间：

外层高度 H = 400vh，视口高度 V = 100vh cover 范围总长度 = H + V （元素顶边碰到视口底边 → 元素底边离开视口顶边） 钉住开始 = 外层顶边到达视口顶边 = 已滚动 V 钉住结束 = 外层底边到达视口底边 = 已滚动 H ⇒ animation-range: cover 100vh cover calc(100% - 100vh) （百分比以 cover 总长度 H + V 为基准，所以 100% - 100vh = H）
对比：JS 版每一帧要读布局（getBoundingClientRect）再写样式；滚动由合成器先走，JS 稍后才跟上，所以开启“主线程压力”后，球体会明显滞后于画面。CSS 版里 scale / rotate / filter 可在合成器线程插值，仍然与滚动同步。

03 · Parallax

视差滚动

各图层只差一个 --s，JS 与 CSS 共用同一组数值

原理与实现：视差

视差 = 不同图层以不同比例响应同一个滚动

设区块的穿越进度为 t（0→1，即 cover 范围），每层有一个速度量 --s，位移 = lerp(-s, s, t)。正数 = 比页面慢（远景，如太阳、星空），负数 = 比页面快（近景，如云、前景山）。本页两种实现读取的是同一组 --s，所以画面应当一致。

实战要点：只动画 translate / transform；父容器 overflow:hidden 防止位移后露边（最前景山脉故意向下多铺了一截）；避免 background-attachment: fixed（移动端不稳定）；也可以用 perspective + translateZ 的纯 CSS 3D 视差，但它要求内容放在独立滚动容器内。

原理与实现：Sticky

sticky 本身是怎么工作的

  • 元素在最近的滚动祖先里先按正常流动，滚到 top 阈值后被“钉住”，直到父元素（containing block）的底边追上它，随后跟着父元素一起离开。
  • 失效的常见原因：祖先设置了 overflow: hidden / auto（成了新的滚动祖先）、父元素高度不够、没有写 top。
  • 叠卡效果：每张卡的 top 依次增加 26px，并给每张卡一段 margin-bottom 作为“滚动跑道”。

难点：钉住之后元素自己的位置不再变化

想让被盖住的卡片缩小，需要一个“被覆盖进度”。但卡片被钉住后，它自己的 view 进度已经停滞，不能用自身的时间线。解决办法是借用“下一张卡”的位置：下一张卡从下方滑到钉住位置的最后 340px，就是上一张被覆盖的过程。

对比：IntersectionObserver 版是“跨过阈值就切换 class”，变化是离散的，由 transition 补间；CSS 时间线版是连续的，随滚动细腻变化、可倒放。叠卡的 range 用 340px / 26px 这类数值手工估算，卡片高度或 top 改了就要同步改，这是 CSS 方案目前最大的维护成本。

原理与实现：Scroll Snap

吸附是怎么工作的

  • 容器：scroll-snap-type: y mandatory。轴向 + 严格度，mandatory 滚动结束必定停在某个吸附点，proximity 只在靠近时才吸附。
  • 子项：scroll-snap-align: start | center | end 声明吸附点；scroll-snap-stop: always 禁止一次滑动越过多个面板。
  • 用 scroll-padding / scroll-margin 调整对齐偏移（比如让出固定导航栏）。
  • 吸附由浏览器的滚动系统完成，通常无需 JS，触摸惯性与键盘操作自动适配。较新的 Chrome 还提供 scrollsnapchange 事件，用来在吸附到新面板时更新状态。

与动画结合：scroller 是谁

view() 默认以最近的祖先滚动容器作为 scroller，所以放在 .snap-box 里的元素，它的进度就是“在这个盒子里滚动到哪了”，不是整页。横向轴用 view(inline)。JS 版则需要监听容器自己的 scroll 事件，并相对容器边界来算进度。

07 · 总结

怎么选？

不是“CSS 取代 JS”，而是各管一段：连续的滚动映射交给 CSS，离散的触发与复杂逻辑留给 JS，并做好渐进增强。

维度JSCSS animation-timeline
主线程依赖每次滚动都要跑回调，繁忙时掉帧可合成属性在合成器线程运行，不受主线程阻塞
与滚动同步回调晚于滚动，快速滚动会滞后/漂移由滚动线程驱动，同帧同步
灵活性任意逻辑、状态、联动 Canvas / WebGL只有“进度 → 样式”的连续映射
一次性触发IntersectionObserver，简单可靠不适合；入场是可倒放的“拖动”
浏览器支持几乎所有浏览器Chrome / Edge 115+、Safari 26+；Firefox 稳定版仍需实验开关（以 MDN / caniuse 最新数据为准）
代码量 / 维护要写监听、测量、节流、清理声明式更短，但 range 有时需手工估算长度
调试断点、console，直观需用 DevTools 的 Animations 面板观察时间线

✅ 优先用 CSS 的场景

阅读进度条、元素随滚动渐变 / 位移、视差、sticky 区域内的联动、横向滚动。这些都是“进度 → 样式”的映射。

✅ 仍用 JS 的场景

一次性入场、计数、懒加载、需要判断与状态的逻辑、联动 Canvas / WebGL / 视频帧序列、需要兼容旧浏览器。

✅ 混合 / 渐进增强

先写好无动画也完整可读的页面；支持时交给 CSS，不支持时回退到 JS 或直接静态显示。

落地模板：渐进增强 + 无障碍

实战清单

  1. 只对 transform / translate / scale / rotate / opacity 做动画，避免触发布局（宽高、top / left）。
  2. animation 简写之后再写 animation-timeline；注意 animation-range 的长度写法需与布局保持一致。
  3. JS 路线：passive 监听 + requestAnimationFrame 合并；先批量读布局再批量写样式；不用时记得 disconnect / removeEventListener。
  4. 尊重 prefers-reduced-motion；动画只做增强，不承载关键信息。
  5. 调试 CSS 时间线：Chrome DevTools 的 Animations 面板与 Elements 里的 animation-timeline 计算样式。
  6. 用本页的“🔥 主线程压力”做自测：同样的效果，在你的页面里换成哪种实现，在低端设备上更稳。
